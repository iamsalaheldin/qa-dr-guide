02 / Playwright setup

What makes --project=dr work?

The CLI option selects a Playwright project. The project and its supporting fixtures do the routing. The command itself doesn't know any DR IPs.

Template: playwright.config.ts

Configure the Chromium browser to resolve the Production hostname to the DR server. The original baseURL stays unchanged.

TYPESCRIPT · FICTIONAL EXAMPLE — REPLACE VALUES
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [{
    name: 'dr',
    use: {
      ...devices['Desktop Chrome'],
      baseURL: 'https://portal.example.com',
      launchOptions: {
        args: [
          '--host-resolver-rules=' +
          'MAP portal.example.com 203.0.113.10, ' +
          'MAP api.example.org 198.51.100.20, ' +
          'MAP *.example.com ~NOTFOUND, ' +
          'MAP example.com ~NOTFOUND, ' +
          'MAP *.example.org ~NOTFOUND, ' +
          'MAP example.org ~NOTFOUND'
        ]
      }
    }
  }]
});

Important: These are fictional demonstration mappings, not runnable DR destinations or a complete implementation. Before using this snippet, replace every example hostname/IP and the protected-domain rules with values approved for your own product; implement Node/API and global-setup routing separately. Do not replace your existing projects when integrating.

B

Browser: Chromium routing

--host-resolver-rules maps allowed hosts to DR IPs, with a fail-closed rule for unlisted Production hosts.

N

Node.js / API traffic

Use a DR-aware fixture or equivalent routing for Playwright request, page.request and other Node HTTP clients. Browser flags don't cover them.

G

Global setup

If your globalSetup signs in or calls services, install the same Node routing there — it's a separate process.

03 / Run on your machine

Try the routing. Then run the tests.

After substituting real, approved values, first verify your hostname can connect to its DR IP. Then run the configured Playwright project.

Quick network proof with curl

--resolve applies only to this curl request. It keeps the hostname and HTTPS certificate validation while using the specified DR IP.

WINDOWS CMD · REPLACE SAMPLE HOST/IP
curl.exe --noproxy "*" --resolve portal.example.com:443:203.0.113.10 -sS -o NUL -w "HTTP: %{http_code} | Server IP: %{remote_ip}\n" https://portal.example.com/
MACOS / LINUX · REPLACE SAMPLE HOST/IP
curl --noproxy '*' --resolve portal.example.com:443:203.0.113.10 -sS -o /dev/null -w 'HTTP: %{http_code} | Server IP: %{remote_ip}\n' https://portal.example.com/
Illustrative output (not a real response): HTTP: 200 | Server IP: 203.0.113.10
Replace the fictional hostname and IP before running this command. A 2xx/3xx response is common for a healthy endpoint, but other status codes may occur because of authentication or WAF rules. The key routing evidence is remote_ip. No TLS-verification bypass is used.

05 / Evidence, not assumptions

Prove the destination is DR.

Treat the destination IP as part of the test evidence. A green test result alone cannot tell you whether a request was sent to DR.

01

Before the run

curl --resolve confirms the local path to the DR IP and returns the remote IP.

02

During the run

Use response.serverAddr() in Chromium and compare its IP with the expected DR host mapping.

03

Across all traffic

Validate relevant browser, API and setup traffic; fail tests on unmapped Production hosts or unexpected IPs.

Example Playwright check

TYPESCRIPT · FICTIONAL HOST/IP
import { test, expect } from './fixtures';

test('Routes browser navigation to DR', async ({ page }) => {
  const response = await page.goto('https://portal.example.com');
  expect(response).not.toBeNull();

  const server = await response!.serverAddr();
  expect(server?.ipAddress?.replace(/^::ffff:/, ''))
    .toBe('203.0.113.10');
});

The test assumes the DR-aware fixture is available at ./fixtures. Adjust the import to your project structure. The hostname and IP are fictional; replace both before running. This checks one browser response, not the entire request graph; proxies may also affect the observed remote address.

06 / Guardrails

DR should be treated like Production.

It can contain real customer records and live integrations. Routing correctly is only half of a safe test run.

✓
Default to read-onlyTag data-changing tests as @writes and exclude them by default.
✓
Never edit the hosts fileKeep mappings inside the test execution. Do not change laptop or shared agent DNS globally.
✓
Block Production fallbackUnlisted protected hosts must fail rather than silently resolving to live Production.
✓
Get write approvalsPurchases, issuance, payments, cancellation, notifications and deletion require DR-owner agreement.
✓
Confirm external servicesSMS, email, payment and government integrations may still be live. Verify before triggering.
✓
Record created dataKeep a record of every test-created entity and share it with the DR owners.

Troubleshooting — common symptoms

Tests pass, but the server IP is a Production IP

Routing may cover the browser but not Node/API requests, or a proxy may resolve names independently. Check all execution paths and inspect proxy settings. Do not trust passing tests until routing is verified.

Timeout when connecting to DR

Verify network reachability from the specific laptop or pipeline agent. Give Infrastructure the source IP, destination DR IP and port 443.

ERR_NAME_NOT_RESOLVED or hostname missing from mapping

This can be the expected fail-closed guard. Request the missing host's DR IP, then add that exact hostname to the approved map.

HTTP 500: “The URL you requested has been blocked”

A WAF may reject automated browser user-agent strings. Use an appropriate browser user-agent if approved and troubleshoot with the DR/WAF owners.

Certificate verification error

Check the certificate chain and hostname with Infrastructure. Keep TLS verification enabled; don't bypass certificate errors just to get tests passing.

HTTP 502 / 504 or very slow responses

DR may be unavailable or capacity-constrained. Share timestamps, hostnames and timings with DR support.
